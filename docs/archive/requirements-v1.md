## 1. 引言

### 1.1 编写目的

本文档旨在对 FitMind 项目的功能、性能、数据、接口、架构等方面的需求进行系统性描述。文档面向以下读者：

- 产品设计人员：理解完整的功能边界和用户场景
- 后端开发人员：基于接口和数据需求进行实现
- 前端开发人员：基于交互需求和接口契约实现 UI
- 测试人员：基于用例编写测试用例
- 项目管理者：掌握整体需求范围和优先级

### 1.2 产品概述

FitMind 是一个基于对话式 AI 的健身数据记录与管理平台。用户通过自然语言与系统交互，表达训练计划、训练结果、身体状态、饮食摄入等信息，系统利用大语言模型（LLM）将口语化、非结构化的输入转化为结构化数据，并持久化到数据库，形成可追踪、可分析、可回顾的个人健身数据系统。

一句话定义：

> FitMind = 对话式健身记录入口 + LangGraph 状态编排 + 结构化事实落库引擎

### 1.3 项目定位

FitMind 不是一个"陪聊式健身助手"，而是一个"健身数据操作系统"上的对话式 Agent 层。它的核心任务不是回答用户问题，而是把模糊、口语化、多轮补充的健身表达，转化为可靠的结构化事实。

## 2. 项目背景与目标

### 2.1 业务背景

在真实的健身场景中，用户不会按表单逐字段填写训练数据，而是直接说自然语言，例如：

- "今天练胸，卧推 60kg 5x5，再做上斜哑铃推举和夹胸。"
- "本来计划跑 8 公里，最后只跑了 5 公里，状态一般，后两公里掉速很厉害。"
- "今天睡得不好，腿有点酸，训练轻一点。"
- "晚饭吃了鸡胸肉、米饭和一杯蛋白粉。"
- "把刚才的卧推改成 55kg，不是 60kg。"

现有健身 App 多采用表单录入模式，对用户输入的灵活性支持不足，导致记录过程繁琐、用户留存率低。FitMind 通过对话式交互降低录入门槛，同时借助 LLM 的理解能力实现信息的结构化沉淀。

### 2.2 核心目标

1. **降低记录门槛**：通过对话式自然语言交互替代表单填写
2. **结构化沉淀**：将非结构化健身表达转化为标准化的数据库记录
3. **数据可追溯**：完整保存对话历史、LLM 调用轨迹和落库记录
4. **长期个性化**：通过三层记忆系统建立用户的长期健身画像
5. **数据驱动分析**：支撑后续的日报、周报、趋势分析和智能建议

### 2.3 核心问题

项目要解决的核心问题不是"如何回答用户"，而是"如何把模糊、口语化、多轮补充的健身表达，转成可靠的结构化事实"。

具体包含：

- 非结构化输入的理解和分类
- 多意图混合输入的拆分
- 多轮补充与纠错的支持
- 计划与实际结果的分离
- 训练、恢复、饮食之间的上下文关联
- 落库前的歧义消解与字段补全

## 3. 范围定义

### 3.1 第一阶段（V1）包含的能力

| 编号 | 能力领域 | 描述 |
|------|---------|------|

| C-02 | 训练结果记录 | 支持记录实际训练完成情况，包括完成度、主观强度、是否调整 |
| C-03 | 身体状态记录 | 支持记录睡眠、疲劳、酸痛、心理状态、身体异常等信息 |
| C-04 | 饮食记录 | 支持记录每日餐次、食物、补剂、粗粒度营养估算 |
| C-05 | 纠错与修改 | 支持用户在中途或事后修改已记录的数据 |
| C-06 | 查询与回顾 | 支持用户查询当天或近期的训练、饮食、状态汇总 |
| C-07 | 对话日志保存 | 保存完整的用户-Agent 对话历史，支持上下文回溯 |
| C-08 | 用户长期记忆 | 支持用户显式设定偏好，支持 Agent 自动提炼长期画像 |
| C-09 | 会话管理 | 支持多线程、多会话结构，提供会话摘要机制 |
| C-10 | 用户认证 | 支持用户注册、登录、身份验证 |

### 3.2 第一阶段不包含的能力

| 编号 | 能力领域 | 说明 |
|------|---------|------|
| N-01 | 自动生成个性化训练周期计划 | 系统不自动编排长期训练计划，仅记录用户自行设定的计划 |
| N-02 | 医疗诊断 | 不提供任何形式的医学诊断或医疗建议 |
| N-03 | 严格营养计算 | 不做克级精准的营养成分分析 |
| N-04 | 动作视觉识别 | 不通过图像或视频分析动作质量 |
| N-05 | 可穿戴设备数据同步 | 不与手环、手表等可穿戴设备直接对接 |
| N-06 | 多语言支持 | V1 仅支持中文对话 |

## 4. 功能性需求

### 4.1 用户认证模块

#### FR-AUTH-001：用户注册

**描述**：新用户可通过提供邮箱、用户名、密码完成账号注册。

**输入**：
- 邮箱（必填，唯一）
- 用户名（必填，唯一）
- 密码（必填，加密存储）

**输出**：注册成功 / 失败提示

**业务规则**：
- 邮箱格式合法性校验
- 用户名长度 2-30 字符
- 密码长度不少于 6 字符
- 密码使用哈希加密后存储，明文不可逆
- 邮箱和用户名需全局唯一

#### FR-AUTH-002：用户登录

**描述**：已注册用户通过邮箱/用户名 + 密码登录系统。

**输入**：
- 邮箱或用户名（必填）
- 密码（必填）

**输出**：登录成功 / 失败提示 + 用户会话令牌

**业务规则**：
- 支持邮箱或用户名二选一登录
- 登录成功后更新 `last_login_at`
- 用户状态为 `disabled` 或 `deleted` 时拒绝登录

#### FR-AUTH-003：用户个人资料管理

**描述**：用户可设置和修改个人健身背景信息。

**输入参数**：
- 性别、出生日期、身高、体重、目标体重
- 健身目标（减脂/增肌/维持/运动表现提升）
- 训练水平（新手/初级/中级/高级）
- 受伤记录、医疗注意事项
- 饮食偏好、偏好训练日

**业务规则**：
- 一个用户对应一条个人资料

### 4.2 对话交互模块

#### FR-CHAT-001：发送对话消息

**描述**：用户通过自然语言发送健身相关消息，系统返回结构化的回执和总结。

**输入**：
- `user_id`：用户标识
- `thread_id`：对话线程标识
- `message`：用户自然语言文本
- `system_prompt`（可选）：系统提示词
- `model`（可选）：指定 LLM 模型
- `temperature`（可选）：LLM 温度参数
- `persist_log`（可选）：是否持久化对话日志

**输出**：
- 用户 ID、线程 ID、会话 ID
- 识别的意图类型
- 使用的模型
- Agent 生成的自然语言回复
- （可选）结构化落库回执

**处理流程**：
1. 接收用户消息并保存至 `conversation_logs`
2. 解析或创建当前 `chat_sessions`
3. 构建对话上下文（系统提示词 + 最近 5 轮历史 + 当前消息）
4. 调用 LLM 进行意图识别和内容理解
5. 根据意图路由到对应领域子 Agent（计划/训练/状态/饮食/纠错/查询）
6. 子 Agent 输出结构化事实
7. 校验、归一化、合并事实
8. 如有歧义，向用户发起确认请求
9. 无歧义时写入对应业务表
10. 生成回复并保存至 `conversation_logs`

#### FR-CHAT-002：流式对话

**描述**：支持 Server-Sent Events (SSE) 流式返回 Agent 回复，改善用户体验。

**输入**：与 FR-CHAT-001 相同

**输出**：SSE 事件流，包含以下事件类型：
- `session`：会话创建/确认事件
- `delta`：逐词/逐段增量文本
- `done`：对话完成事件（含完整回复和元数据）
- `error`：错误事件

**业务规则**：
- 前端需正确解析 `text/event-stream` 格式
- 连接异常中断时应能重连

#### FR-CHAT-003：原始 LLM 调用

**描述**：提供原始 LLM 调用接口，不经过对话上下文构建和持久化流程，用于调试或特殊场景。

**输入**：
- `messages`：消息列表（system / user / assistant 角色）
- `model`（可选）：LLM 模型
- `temperature`（可选）：温度参数

**输出**：LLM 原始响应内容

### 4.3 训练管理模块

#### FR-TRAIN-001：记录训练计划

**描述**：用户通过自然语言表达训练计划意图，系统提取并结构化存储。

**示例输入**：
> 这周我想练三天：周一胸肩三头，周三背二头，周五腿

**结构化输出关注点**：
- 训练部位 / 主题
- 计划动作名称
- 每个动作的目标组数、次数、重量
- 有氧项目的距离、时长、配速
- 计划训练强度（RPE）

**落库方式**：
- `user_workout_plans`：保存计划原文和日期
- `raw_text` 优先保存原文，逐步补全结构

#### FR-TRAIN-002：记录实际训练结果

**描述**：用户完成训练后，通过对话记录实际完成情况。

**示例输入**：
> 今天练胸，卧推 60kg 5x5，上斜哑铃推举 4 组 12 次，夹胸 3 组，状态还不错

**结构化输出关注点**：
- 实际完成的动作和组次
- 与计划的偏差（未完成/替换/加练）
- 主观训练强度（perceived exertion 1-10）
- 能量水平（1-10）
- 训练中的情绪和异常

**落库方式**：
- `user_workout_records`：一天一条主记录（`user_id` + `record_date` 唯一）
- `user_workout_record_items`：每条记录下挂多条动作明细

**业务规则**：
- 同一天同一用户只能有一条训练主记录
- 如当天已存在记录，后续消息应为补充或修改

#### FR-TRAIN-003：修改已记录训练

**描述**：用户可以纠正或修改之前记录的训练数据。

**示例输入**：
> 把刚才的卧推改成 55kg，不是 60kg

**处理步骤**：
1. 识别为修改意图
2. 根据上下文定位目标记录
3. 提取变更内容
4. 如有歧义（多条可能目标），向用户确认
5. 执行更新并返回回执

### 4.4 身体状态模块

#### FR-COND-001：记录身体状态

**描述**：用户记录每日睡眠、疲劳、酸痛、心理状态等信息。

**示例输入**：
> 昨晚睡了 6 小时，今天有点疲劳，腿很酸，但是精神状态还行

**结构化输出关注点**：
- 睡眠时长
- 疲劳程度（1-10）
- 压力程度（1-10）
- 酸痛程度（1-10）
- 当前体重
- 情绪描述

**落库方式**：
- `user_body_status_records`：一天一条（`user_id` + `record_date` 唯一）
- 能解析的字段填入结构化列，无法解析的保留 `raw_text`

**业务规则**：
- 同一天同一用户只能有一条身体状态记录
- 支持只记录部分字段，其余为空

### 4.5 饮食管理模块

#### FR-NUTR-001：记录饮食摄入

**描述**：用户通过对话记录每日饮食内容。

**示例输入**：
> 今天早餐吃了鸡蛋燕麦，午饭吃了鸡胸米饭和西兰花，晚上喝了蛋白粉

**结构化输出关注点**：
- 餐次（早/午/晚餐/加餐）
- 食物名称
- 份量描述
- 补剂名称和用量
- 粗粒度营养估算（卡路里、蛋白质、碳水、脂肪）

**落库方式**：
- `user_nutrition_records`：一天一条（`user_id` + `record_date` 唯一）
- V1 核心保存 `raw_text`，营养估算字段可为空

**业务规则**：
- 同一天同一用户只能有一条饮食记录
- 一天内多次补充饮食信息，应合并到同一条记录

### 4.6 查询与分析模块

#### FR-QUERY-001：查询当日记录

**描述**：用户查询当天所有已记录的健身数据汇总。

**示例输入**：
> 今天都记录了什么？ / 今天的训练总结一下

**输出内容**：
- 当日训练计划及完成情况
- 当日饮食记录概要
- 当日身体状态概要
- 计划与实际的偏差

#### FR-QUERY-002：查询近期记录

**描述**：用户查询近期（如最近三天、本周、上周）的健身数据汇总。

**示例输入**：
> 回顾最近三天训练 / 这周练了几天 / 上周饮食怎么样

**输出内容**：
- 指定时间范围内的训练记录汇总
- 训练频率、完成度趋势
- 饮食模式概要
- 身体状态变化趋势

### 4.7 记忆系统模块

#### FR-MEM-001：用户显式记忆管理

**描述**：用户可以显式要求系统记住特定偏好或设定。

**示例输入**：
> 以后回答简洁一点，我现在主要目标是减脂，一周练四天，膝盖有旧伤避免跳跃

**记忆分类**：

| 分类 | 说明 | 示例 |
|------|------|------|
| `fitness_preference` | 健身偏好 | 减脂/增肌目标、每周训练天数 |
| `content_preference` | 内容偏好 | 简洁/详细、列表/段落 |
| `conversation_preference` | 对话风格 | 少鼓励多结论、一次只问一个问题 |
| `diet_preference` | 饮食约束 | 高蛋白、控碳、乳糖不耐 |
| `health_constraint_preference` | 健康限制 | 膝盖旧伤、避免冲击动作 |

**业务规则**：
- 同一 `memory_key` 的新值覆盖旧值（旧值标记 `archived`）
- 用户显式记忆优先级高于 Agent 推断记忆
- 每条记忆记录原始来源（`source_conversation_log_id`）

#### FR-MEM-002：Agent 自动记忆提取

**描述**：系统基于用户历史对话和业务记录，自动提炼长期用户画像记忆。

**记忆分类**：

| 分类 | 说明 | 示例 |
|------|------|------|
| `fitness_goal_memory` | 健身目标 | 当前主要目标、阶段目标 |
| `training_pattern_memory` | 训练模式 | 常用分化训练、每周频率、训练时段 |
| `exercise_preference_memory` | 动作偏好 | 常做动作、回避动作 |
| `body_status_baseline_memory` | 状态基线 | 睡眠模式、恢复速度、高风险区域 |
| `nutrition_pattern_memory` | 饮食模式 | 饮食结构、营养习惯 |
| `conversation_style_memory` | 交互风格 | Agent 归纳的对话风格偏好 |
| `current_phase_memory` | 当前阶段 | 恢复期、忙碌期、重新控制期 |
| `adherence_risk_memory` | 执行风险 | 容易中断的情况、记录持续性薄弱点 |

**业务规则**：
- 每条记忆包含 `confidence_score`（0-1）表征可信度
- 记忆支持 `active` / `superseded` / `expired` 三种状态
- 新版本不覆盖旧版本，旧版本标记为 `superseded`
- 记忆有效期为 `valid_from` 到 `valid_to`

#### FR-MEM-003：会话与短期记忆管理

**描述**：系统管理单次对话会话，维护短期上下文。

**会话生命周期**：
1. 创建会话（`chat_sessions.status = active`）
2. 消息持续写入（`last_message_at` 更新）
3. 达到消息阈值时生成 `running_summary`
4. 会话结束时生成 `final_summary`（`status = closed`）
5. 长期未使用标记为 `archived`

**会话摘要类型**：
- `running_summary`：会话进行中生成的增量摘要
- `final_summary`：会话结束时生成的完整摘要
- `memory_candidate`：可供长期记忆提炼的候选摘要

## 5. 非功能性需求

### 5.1 性能需求

| 编号 | 指标 | 要求 |
|------|------|------|
| NFR-P01 | 对话响应时间（同步） | P95 < 8 秒（含 LLM 调用） |
| NFR-P02 | 流式首字延迟 | P95 < 2 秒 |
| NFR-P03 | 数据库写入延迟 | P95 < 500ms |
| NFR-P04 | 查询接口响应时间 | P95 < 3 秒 |
| NFR-P05 | 并发支持 | 单实例支持 50+ 并发 SSE 连接 |

### 5.2 可用性需求

| 编号 | 指标 | 要求 |
|------|------|------|
| NFR-A01 | 系统可用性 | 99.5%（V1 阶段） |
| NFR-A02 | 服务降级 | LLM 异常时返回友好错误提示而非崩溃 |
| NFR-A03 | 数据持久性 | 数据库主从或备份，不丢失已落库数据 |
| NFR-A04 | SSE 重连 | 前端应支持断线重连机制 |

### 5.3 安全性需求

| 编号 | 指标 | 要求 |
|------|------|------|
| NFR-S01 | 密码存储 | 使用安全哈希算法（bcrypt / argon2），不可逆 |

### 5.4 可维护性需求

## 6. 用户场景与用例

### 6.1 场景一：新用户首次使用

**角色**：首次使用的健身用户

**前置条件**：用户已安装并打开 FitMind，尚未注册

**主流程**：
1. 用户进入登录页，看到品牌介绍和高亮功能卡片
2. 用户点击"注册"切换至注册表单
3. 用户填写邮箱、用户名、密码
4. 系统校验输入合法性，创建用户账号
5. 用户进入聊天工作区
6. 系统发送欢迎消息，介绍 FitMind 的基本功能
7. 用户通过快捷提示了解可记录的内容类型

**后置条件**：用户已注册并进入聊天工作区

### 6.2 场景二：记录一次完整训练

**角色**：已完成当日训练的健身用户

**前置条件**：用户已登录，当日尚未记录训练

**主流程**：
1. 用户输入：`今天练胸，卧推 60kg 5x5，上斜哑铃推举 4 组 12 次，夹胸 3 组，状态还不错`
2. 系统识别意图为"训练记录"
3. 系统调用 Workout Result Agent 提取结构化事实
4. 系统解析出：
   - 动作 1：卧推，60kg，5组5次
   - 动作 2：上斜哑铃推举，4组12次
   - 动作 3：夹胸，3组
   - 主观感受：状态不错
5. 系统写入 `user_workout_records`（1条）+ `user_workout_record_items`（3条）
6. 系统保存对话日志
7. 系统返回回执：`已记录今天的训练：胸训 3 个动作，总组数 12 组，主观感受良好。`

**异常流程**：
- 如当天已有训练记录 → 系统询问：是补充还是替换今天的记录？
- 如部分信息模糊（如哑铃推举重量未知） → 系统追问重量

### 6.3 场景三：多轮纠错

**角色**：记录后需要纠正的用户

**前置条件**：用户刚刚记录了一次训练

**主流程**：
1. 用户输入：`把刚才的卧推改成 55kg，不是 60kg`
2. 系统识别意图为"修改"
3. 系统定位最近一条对话中的卧推记录
4. 系统更新对应 `user_workout_record_items` 的重量
5. 系统返回：`已将卧推重量更新为 55kg。`
6. 用户输入：`对了，还忘了说做完后做了 10 分钟拉伸`
7. 系统识别为对今日训练的补充
8. 系统将拉伸添加为训练记录的新条目
9. 系统返回确认消息

### 6.4 场景四：综合记录（混合意图）

**角色**：一次性报告当日整体情况的用户

**前置条件**：用户已登录

**主流程**：
1. 用户输入：`今天练了腿，深蹲 80kg 3x5，腿举 4 组。睡了 7 小时状态还可以。晚饭吃了牛排和土豆。`
2. 系统识别为复合意图：
   - 训练结果：腿训（深蹲、腿举）
   - 身体状态：睡眠 7 小时、状态可
   - 饮食：牛排、土豆
3. 系统依次调用 Workout Result Agent、Condition Agent、Nutrition Agent
4. 系统合并三个领域的事实
5. 系统分别写入三张业务表
6. 系统返回综合回执

### 6.5 场景五：设定长期偏好

**角色**：希望系统记住自己偏好的用户

**前置条件**：用户已登录

**主流程**：
1. 用户输入：`以后回答简洁一点，我主要目标是减脂，一周训练四天，膝盖有旧伤避免跳跃动作`
2. 系统识别为记忆设定意图
3. 系统提取三条记忆：
   - memory_key=response_style → "简洁"
   - memory_key=goal_type → "减脂"
   - memory_key=preferred_training_days → "4"
   - memory_key=health_constraint → "膝盖旧伤，避免跳跃"
4. 系统写入 `user_defined_memories`（4条）
5. 系统返回：`已记住：回答风格简洁、减脂目标、每周 4 练、膝盖保护。`

### 6.6 场景六：查询近期训练

**角色**：希望回顾近期训练情况的用户

**前置条件**：用户已有至少 3 天的训练记录

**主流程**：
1. 用户输入：`回顾一下最近三天的训练`
2. 系统识别意图为"查询"
3. 系统查询最近 3 天的 `user_workout_records`
4. 系统汇总训练天数、训练部位、主要动作
5. 系统调用 Insight Agent 生成自然语言解释
6. 系统返回汇总报告

### 6.7 场景七：会话长时间交互

**角色**：在一次会话中大量交互的用户

**前置条件**：用户已登录，当前会话已有 15+ 条消息

**主流程**：
1. 会话消息数量达到阈值
2. 系统触发运行中摘要生成（`running_summary`）
3. 系统将前 10 条消息压缩为摘要
4. 后续消息使用摘要 + 最近 5 条消息作为上下文
5. 用户结束会话
6. 系统生成 `final_summary` 并关闭会话
7. 系统可选触发长期记忆提炼

### 7.1 核心数据实体

系统包含 12 张核心表：

| 编号 | 表名 | 描述 | 所属层级 |
|------|------|------|---------|
| T-01 | `users` | 用户账号信息 | 用户层 |
| T-02 | `user_profiles` | 用户健身特征（1:1） | 用户层 |
| T-03 | `user_workout_plans` | 训练计划原文 | 业务层 |
| T-04 | `user_workout_records` | 每日训练主记录 | 业务层 |
| T-05 | `user_workout_record_items` | 训练动作明细 | 业务层 |
| T-06 | `user_nutrition_records` | 每日饮食记录 | 业务层 |
| T-07 | `user_body_status_records` | 每日身体状态 | 业务层 |
| T-08 | `conversation_logs` | 对话历史日志 | 对话层 |
| T-09 | `user_defined_memories` | 用户显式记忆 | 记忆层 |
| T-10 | `agent_derived_memories` | Agent 推断记忆 | 记忆层 |
| T-11 | `chat_sessions` | 对话会话管理 | 记忆层 |
| T-12 | `chat_session_summaries` | 会话摘要 | 记忆层 |

### 7.2 数据关系

```
users
  └── user_profiles (1:1)
  ├── user_workout_plans
  ├── user_workout_records
  │     └── user_workout_record_items
  ├── user_nutrition_records
  ├── user_body_status_records
  ├── conversation_logs
  ├── user_defined_memories
  ├── agent_derived_memories
  └── chat_sessions
        ├── chat_session_summaries
        └── conversation_logs
```

### 7.3 数据存储策略

- **原文优先**：第一版中，许多字段以 `raw_text` 保存用户原始输入，后续逐步结构化
- **按天聚合**：训练记录、饮食记录、身体状态记录均以用户一天一条为粒度
- **不可变审计**：对话日志（`conversation_logs`）不可删除或修改，保证审计完整性
- **版本化管理**：Agent 记忆通过新增版本（`superseded`）而非覆盖旧版本

## 9. 系统架构需求

### 9.1 整体架构

系统采用前后端分离架构：

- **前端**：React 19 + Vite 8 + Tailwind CSS 4 SPA
- **后端**：Python 3.11+ FastAPI + SQLAlchemy 2.0 + Alembic
- **AI 引擎**：LangGraph（状态编排）+ OpenAI 兼容 LLM 接口
- **数据库**：MySQL 8.0+

### 9.2 Agent 架构

采用 `IntentClassifier → IntentRouter → ServiceChain → Persistence` 的服务链架构：

```
User
  → ChatService               (主编排器，session 管理)
    → IntentClassifier        (关键词规则 + LLM 双模分类)
    → IntentRouter            (意图 → 模块路由)
    → ServiceChain            (按优先级依次尝试)
      → NutritionRecordService   (饮食 ReAct 提取)
      → BodyStatusRecordService  (身体状态轻量抽取)
      → WorkoutRecordService     (训练记录提取)
      → WorkoutPlanService       (长期计划更新)
    → fallback: general LLM chat
```

注：所有业务写入经过草稿确认机制（draft → confirm → persist）。

### 9.3 技术栈约束

| 层级 | 技术选型 | 约束 |
|------|---------|------|
| 前端框架 | React 19 | 使用 Vite 构建 |
| 样式方案 | Tailwind CSS 4 | 深色主题为主 |
| 后端框架 | FastAPI | 异步模式 |
| ORM | SQLAlchemy 2.0 | 使用 Mapped 声明式映射 |
| 数据库迁移 | Alembic | 所有 schema 变更需通过迁移脚本 |
| LLM 客户端 | OpenAI Python SDK | 兼容任何 OpenAI API 格式的提供商 |
| 工作流引擎 | LangGraph | 仅用于营养 ReAct 循环；整体链路为顺序服务链 |
| 数据库驱动 | PyMySQL | MySQL 8.0+ |

### 9.4 部署架构

```
[浏览器] → [Nginx / CDN] → [Vite 构建产物]
                         → [API 反向代理] → [Uvicorn + FastAPI] → [MySQL]
                                                                    → [LLM API]
```

## 11. 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 意图 | Intent | 用户当前消息的主要目的（记录/修改/查询/确认） |
| 事实 | Fact | 从自然语言中提取并标准化后的结构化数据单元 |
| 落库 | Persist | 将结构化事实写入数据库的操作 |
| 会话 | Session | 一次连续的对话交互过程 |
| 线程 | Thread | 用户与系统的对话线程，一个线程可包含多个会话 |
| 领域服务 | Domain Service | 负责特定领域事实提取和草稿确认的业务模块 |
| 草稿确认 | Draft Confirmation | 提取 → 写入 draft 表 → 用户确认 → 写入正式表的写库安全机制 |
| 校验门控 | Confirmation Gate | 在写入数据库前检查歧义并要求用户确认的机制 |
| 粗粒度营养估算 | Rough Nutrition Estimate | 基于食物名称的大致卡路里和宏量营养素估算 |
| RPE | Rating of Perceived Exertion | 主观训练强度评分（1-10 分） |
| 运行中摘要 | Running Summary | 会话进行中生成的增量式上下文摘要 |
| 最终摘要 | Final Summary | 会话结束时的完整会话摘要 |
| 记忆候选 | Memory Candidate | 可提炼为长期记忆的会话摘要 |
