# FitMind 项目分析与后续开发计划

评审日期：2026-10-29。代码基线：`a63570f`。本报告基于仓库静态阅读，覆盖前后端入口、鉴权、对话编排、草稿写入、数据模型、推荐、上下文、测试与设计文档；不等于完整安全审计或线上验收。

## 1. 总体判断

FitMind 已超过界面原型阶段，具备对话式健身记录 MVP 的主要闭环：账号登录 → 自然语言输入 → 意图识别/澄清 → 领域提取 → 草稿确认 → 结构化保存 → 历史查询与周报。适合进入工程加固与小规模内测阶段，尚不能仅凭已有代码认定具备生产就绪能力。

最有价值的方向是“可靠的个人健身数据入口”。下一阶段应优先确保记录不会错存、重存、跨日错位，并让推荐真正使用用户状态与限制，再扩展多模态、设备接入等功能。

## 2. 目录和技术结构

```text
FitMind/
├─ web/                         React Web 应用
│  ├─ src/auth/                 登录状态、认证上下文
│  ├─ src/lib/                  API 请求与令牌刷新
│  ├─ src/pages/                登录、聊天、训练历史、周趋势
│  ├─ src/components/           Markdown、执行过程展示
│  └─ src/hooks/                自动滚动
├─ agent/                       Python API 与 Agent 业务
│  ├─ src/fitmind_agent/
│  │  ├─ api/                   路由、依赖、身份校验
│  │  ├─ services/              对话编排与领域服务
│  │  ├─ repositories/          数据访问
│  │  ├─ schemas/               请求响应与提取结构
│  │  ├─ db/                    ORM 模型、会话
│  │  ├─ core/                  配置、模型客户端
│  │  ├─ prompts/               按业务组织的提示词
│  │  ├─ domain/                动作分类
│  │  ├─ mcp/                   营养工具服务入口
│  │  └─ graphs/                已弃用的历史占位实现
│  ├─ alembic/                  数据库迁移
│  └─ tests/                    领域、接口与鉴权测试
├─ dataset/                     JSONL 场景、规范、评分参考
└─ docs/                        架构、数据、工作流设计
```

前端依赖声明为 React 19、Vite 8、Tailwind 4、Recharts 3；后端为 Python 3.11+、FastAPI、Pydantic、SQLAlchemy、Alembic，使用 MySQL。模型通过 OpenAI 兼容接口调用，营养流程使用 LangGraph ReAct。以上是仓库声明，不代表已核验第三方版本兼容性。

实际主链路是 `ChatService → 意图分类 → 挂起草稿/澄清策略 → 路由 → 领域服务 → 数据访问`，不是整个系统都由 LangGraph 驱动。保留这种确定性主流程是合理的，无需为架构形式重写为多 Agent 或微服务。

## 4. 已确认的优势

1. API、服务、数据访问、Schema、Prompt 有清楚的目录边界，领域服务能够独立演进。
2. 写入先生成草稿再确认，统计由代码计算，模型主要负责理解与表达，方向适合数据记录产品。
3. 低置信度和冲突意图有持久化澄清机制，比单纯分类后直接写入更稳妥。
4. 鉴权包含 Argon2 密码哈希、刷新令牌哈希存储和轮换、令牌族撤销、用户版本校验；前端访问令牌放在内存，并合并并发刷新请求。
5. 已有迁移、领域测试、意图日志、Token 记录和场景数据集，具备继续建立质量闭环的基础。

## 5. 风险与改进优先级

### P0：进入真实用户内测前处理

**草稿确认缺少统一事务边界。** `workout_record_service.py` 先保存训练记录，再更新草稿状态；`repositories/workout.py` 中这些操作分别提交。中途失败可能出现“记录已保存、草稿仍待确认”，并发确认也有重复保存风险。需要服务层事务、草稿行锁或版本比较、来源草稿唯一约束和请求幂等键，并核查其余三类写入。风险来自代码结构，尚未做并发复现。

**确认语义存在误判。** 训练草稿使用包含关键词判断确认，确认分支先于问题分支。“可以把重量改成55kg吗”含“可以”，可能直接保存旧草稿。应优先识别修正与疑问，按钮提交显式动作和草稿版本；自由文本只接受明确确认，含新数值/修正表达时先更新草稿。训练、饮食、身体状态、计划统一规则。

**日期依赖服务器本地时间。** 多处 `date.today()`、无时区 `datetime.now()` 与 UTC 时间混用。服务器换时区或用户跨时区时存在跨日归属风险。统一 UTC 存储事件时间、用户时区解析业务日期，增加午夜和周边界测试。

**运行错误信息直接返回客户端。** 聊天接口和流异常包含原始异常字符串。需返回稳定错误码与请求编号，详细异常留在脱敏日志；配置错误也应避免暴露内部细节。

**上线运行基础未形成仓库交付。** 未发现受版本管理的 CI、容器/Compose、Python 锁文件和部署配置。补齐自动检查、可复现安装、迁移演练、配置检查、备份恢复与回滚步骤。生产配置还应强制关闭 debug；现有配置默认开启，启动保护主要覆盖鉴权密钥和 Secure Cookie。

### P1：决定产品可靠性和扩展效率

**推荐输入不足。** `today_workout_recommendation_service.py` 的上下文采集只有长期计划与近期训练两项，不能据此认为真实睡眠、疲劳或伤病数据已参与推荐。建立共享用户上下文构建器，明确数据来源、缺失项与限制优先级。

**记忆数据存在，使用闭环不足。** `chat_context.py` 当前组装系统提示、会话摘要、近期消息和当前输入，没有统一注入档案及两层用户记忆。需要按场景选择信息、控制长度，并提供来源和删除传播机制。

**训练字段不利于精确分析。** 动作明细大量使用 `reps_text`、`weight_text`、`duration_text`、`distance_text`。保留原文，同时增加标准数值、单位和逐组记录；区分热身、正式组、单侧和自重，避免直接将文本相乘计算容量。

**大文件增加改动成本。** `ChatWorkspace.jsx` 约109KB，`chat_service.py` 约73KB。按会话、SSE、草稿、档案、记忆拆分前端；后端抽取上下文、待办工作流、事件编码和领域注册。先建立行为回归，再分步拆分。

**评估资产尚未接通执行链。** dataset 文档引用的 `agent/tests/test_dataset.py` 不存在，评分脚本是参考实现。将数据集接到可执行评估器，区分确定性回归和真实模型评估；不能把编辑距离当作充分的语义正确性判据。

**测试覆盖类型不完整。** 前端目前只有 API 客户端测试文件；后端已有较多领域测试，鉴权测试使用 SQLite。仍需 MySQL 迁移、并发事务、完整 SSE 和浏览器业务闭环测试。

**失败与无数据可能混淆。** 推荐查询异常时回退为空列表或空值。应携带每个来源的查询状态，避免下游模型把“读取失败”解释成“用户没有训练”。

### P2：增长与体验

补齐已保存数据的修改/删除、饮食与状态历史、URL 路由和浏览器返回、移动端适配、数据导出/账号删除。随后再评估 PWA、图片记录、设备接入和消息提醒。

## 6. 目标结构

维持前后端分离的模块化单体，数据库继续使用 MySQL。无需先引入微服务、向量库或复杂任务基础设施。

- API 层负责身份、输入校验和响应协议。
- 应用服务负责事务、幂等、工作流状态和领域协调。
- 领域层负责日期、动作/单位归一、统计和业务限制。
- 仓储层负责查询与 flush，事务由应用服务控制。
- LLM/工具层负责模型调用、结构提取、工具适配、预算和超时策略。
- 统一上下文构建器提供档案、限制、记忆、近期事实和来源状态。
- 后台任务先明确可靠性要求；只有确需跨进程重试时再选择持久队列。

## 7. 分阶段开发计划

以下按1名后端/Agent、1名前端共同投入，测试和产品评审兼职估算。共约16—22周，是排期假设，不是交付承诺；单人串行开发应重新估算。阶段按验收结果推进。

| 阶段 | 预计 | 交付内容 | 验收条件 |
|---|---|---|---|
| M0 可运行基线 | 1周 | 环境说明、依赖锁定、测试基线、CI、测试数据库、文档修复 | 新环境可按文档启动；自动检查可执行且结果留档；失败项明确归因 |
| M1 可靠写入 | 2—3周 | 统一确认协议、草稿版本、事务、幂等、时区、错误协议 | 重复/并发确认只产生一次业务记录；模拟失败不出现半提交；修正疑问不触发确认；跨日正确 |
| M2 数据管理闭环 | 3—4周 | 逐组模型、动作与单位标准、历史编辑删除、饮食餐次/状态历史、迁移 | 旧数据可迁移且原文保留；改删可追溯；列表/统计同步；越权操作被拒绝 |
| M3 个性化与评估 | 3—4周 | 共享上下文、伤病约束、记忆来源/冲突/确认、评估运行器、Prompt版本 | 推荐可追溯到真实输入；缺数据有明确说明；用户可查看/撤回记忆；固定评估集可重复运行 |
| M4 计划与分析 | 3—4周 | 结构化周期计划、执行关联、完成率、逐组容量/PR、多周期趋势、成本视图 | 固定样本统计可手工复核；不混淆缺失与零值；计划修改保留版本；估算费用有标记 |
| M5 产品内测与部署 | 3—4周 | 移动端、路由、SSE恢复/取消、邮箱验证/找回密码、限流、监控、备份、导出/注销 | 完整浏览器流程通过；MySQL迁移与恢复演练成功；发布可回滚；内测问题完成分级处理 |
| M6 扩展试点 | 1—2周起 | 从图片辅助记录、PWA、权威营养源、设备接入中选择一项 | 根据内测需求选型；有独立效果/成本指标；扩展失败不影响基础记录 |

### 首个两周迭代

1. 第1—2天：建立可运行环境和测试基线，修正文档断链，记录 MySQL、模型与配置要求。
2. 第3—4天：接入 CI，增加 MySQL 迁移验证和关键记录闭环测试。
3. 第5—7天：修复确认误判，统一显式动作、草稿版本与自由文本规则。
4. 第8—10天：先完成训练记录事务与幂等，再推广至其他草稿；加入重复提交、失败回滚测试。

时区与错误脱敏可接续在 M1 中完成；若依赖安装或迁移发现阻塞，优先解决基线，不以日期替代验收。

## 8. 数据与接口演进清单

建议新增逐组训练表、标准动作与别名、计划版本与计划项、饮食餐次与食物项、记忆来源/版本、审计事件。草稿增加版本、过期、确认关联和幂等信息；用户增加时区。具体表名和字段由 M2 设计评审确定。

迁移遵循“先增字段/表 → 兼容读取 → 可回放回填 → 核对 → 切换 → 延后清理”，避免强行把不确定的历史文本变成精确数值。

接口优先补齐：草稿确认/修正/取消显式命令、已保存记录编辑删除、餐次与状态历史、计划执行关联、账号导出/删除。前端逐步使用 URL 路由；SSE 事件增加协议版本、请求编号、序号和明确终态，重连需避免重复执行写入。

## 9. 质量与发布门槛

- 确定性测试：单位归一、日期、周统计、确认语义、状态迁移。
- 数据库集成：MySQL迁移、事务回滚、并发确认、刷新令牌轮换与多用户隔离。
- 浏览器测试：注册登录 → 输入 → 修正草稿 → 确认 → 刷新 → 历史可见 → 改删 → 退出。
- 故障测试：模型超时、工具失败、数据库错误、断流、过期登录、重复提交。
- 模型评估：意图、事实字段、纠错、多意图与对抗表达；冻结评估集并保存模型/Prompt版本、耗时与Token。
- 运营指标：草稿确认率、确认后纠错率、误写入数量、分类/提取失败率、首事件与首文本耗时、每轮成本、查询失败率、数据覆盖率。

建议的初始质量目标：固定并发/重放测试中重复写入为0；越权回归全部通过；关键业务流程全部通过。模型准确率和性能目标先测基线，再按场景设阈值，不能在没有测量时声称达到某个百分比。
