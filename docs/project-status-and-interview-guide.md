# FitMind 开发现状与面试指南

## 1. 一句话定位

FitMind 是一个面向健身场景的对话式数据入口：用户用自然语言描述训练、饮食、睡眠和身体状态，系统通过意图识别、领域工作流和人工确认，将模糊表达转换为可追踪的结构化数据，并据此提供训练回顾、周报和推荐。

## 2. 当前开发进度

### 已完成的核心闭环

- 真实账号系统：注册、登录、Access Token、Refresh Token 轮换、注销、修改密码和多用户资源隔离。
- 对话基础设施：Session、多轮上下文、历史摘要、水位线压缩、SSE 流式回复和 Token 使用统计。
- 意图系统：关键词召回、LLM 结构化分类、置信度策略、候选冲突检测和持久化意图澄清。
- 写入工作流：训练、饮食、身体状态和长期计划均经过“提取、草稿、纠正、确认、落库”。
- 查询工作流：最近健康总结、今日训练推荐、训练历史筛选和自然周趋势分析。
- 营养 ReAct：LangGraph 控制最大循环次数，模型自主调用食物查询、重量估算、营养计算和汇总工具；本地 MCP Server 已提供工具协议。
- Web 客户端：真实鉴权、流式对话、Agent 状态卡片、草稿与澄清交互、训练历史、周报、档案和自定义记忆。
- Android V1：Compose 原生登录、Session、SSE 对话、思考轨迹、草稿和澄清恢复，以及 Room 离线只读缓存。

### 当前代码组织

```text
FitMind/
  agent/    FastAPI API、ChatService 编排、领域 Service、Repository、Alembic
  web/      React 登录、聊天、训练历史与周报页面
  android/  Kotlin + Compose 原生核心对话客户端
  docs/     架构、数据库、记忆、意图和专项设计文档
  dataset/  意图与信息提取测试语料、评估口径
```

数据库结构以 `agent/alembic/versions/` 为唯一迁移来源。服务通过 SQLAlchemy 模型与 Alembic 管理 MySQL 表结构。

## 3. 核心链路

```text
客户端请求
  -> JWT 鉴权并获得可信 user_id
  -> ChatService 恢复 Session、摘要和最近对话
  -> Pending Draft Gate 优先处理未完成草稿
  -> IntentClassifier 使用关键词 + LLM 分类
  -> IntentResolutionPolicy 判断直接执行还是澄清
  -> IntentRouter 选择唯一领域 Service
  -> 查询类直接生成结果 / 写入类生成待确认草稿
  -> SSE 返回 Agent State、Delta、Workflow 和 Done
  -> 对话、意图、Token 与业务数据分别落库
```

## 4. 仍未完成与技术债

- Agent 派生长期记忆目前已有表和 CRUD，但自动抽取、冲突合并、版本管理及稳定注入尚未形成闭环。
- `ChatService` 承担较多主流程编排职责，后续应拆分为明确的命令处理器或子工作流，降低单类复杂度。
- 食物营养数据主要来自本地静态数据，虽然已有 MCP Server 接口，但尚未连接权威远程营养数据库。
- 训练动作的次数、重量、距离和时长尚未完全标准化，因此训练容量、渐进超负荷和计划完成率暂不能可靠计算。
- Web 自动化测试主要覆盖 API Client，页面级和端到端测试不足；Android instrumentation 测试源码已建立，但仍需真机或模拟器持续执行。
- 尚未建设生产部署、集中日志、指标监控、限流、任务队列、数据库备份和告警体系。
- 账号体系暂未提供邮箱验证、忘记密码、MFA、RBAC 和设备会话管理。

## 5. 面试项目介绍模板

我开发了一个基于 FastAPI 和 LangGraph 的健身智能体 FitMind。它不是普通聊天机器人，而是把用户口语化的训练、饮食和身体状态转换成结构化数据。系统先通过关键词和 LLM 完成意图识别，再由安全策略决定直接路由还是发起澄清；写入类请求必须经过草稿确认，查询类请求从真实数据库聚合后再交给模型解释。前端通过 SSE 展示模型输出和 Agent 执行状态，同时实现了 JWT 鉴权、多用户隔离、会话记忆、Token 统计，以及 Web 和 Android 两套客户端。

## 6. 针对性面试问答

### Q1：为什么不直接把用户输入交给大模型，然后执行返回结果？

训练、饮食等数据一旦写错会污染后续分析。FitMind 将 LLM 定位为“理解和提取器”，而不是最终数据库操作者。模型先生成结构化草稿，用户确认后才由确定性代码落库，从而降低幻觉和误操作风险。

### Q2：为什么意图识别采用关键词和 LLM 两层？

关键词路径延迟低、成本低，适合“确认保存”“今天练了什么”等明确表达；LLM 能处理口语、省略和多意图表达。系统保留两者结果和置信度，再由 `IntentResolutionPolicy` 根据写入类、查询类的不同阈值决定执行或澄清，兼顾速度与准确性。

### Q3：低置信度请求如何避免进入错误业务模块？

分类结果不会直接路由。策略层检查置信度、前两名候选差值和多写入冲突；不满足阈值时创建持久化澄清记录。用户可以选择候选、补充文本或取消，两轮仍不明确就安全退出，并且不会创建业务草稿。

### Q4：多轮记忆是怎么实现的？

当前 Session 保留最近 N 轮作为短期窗口，窗口之前的对话压缩到最新 Summary。每轮结束后检查水位线，存在可压缩消息时在线程池中异步更新摘要；同一 Session 使用锁避免两次压缩并发覆盖。加载上下文时组合系统 Prompt、历史 Summary、最近窗口和当前问题。

### Q5：营养 ReAct 与普通结构化提取有什么区别？

普通提取只能根据模型常识猜测，而营养计算需要多步事实和算术。营养链路由 LangGraph 维护状态和最大循环次数，模型自主选择食物查询、份量估算、单项计算或全天汇总工具，并根据 Observation 决定继续调用还是输出最终可入库草稿。工具同时通过 MCP Server 暴露，便于未来替换成远程权威数据源。

### Q6：为什么查询统计由代码计算，LLM 只负责解释？

训练次数、营养均值、周同比等指标必须可复现。服务层并发读取数据后用确定性代码聚合，缺失值不会按零处理；LLM 只接收已经计算好的指标并生成自然语言结论，避免模型算错或虚构数据库事实。

### Q7：SSE 协议如何支持 Agent 状态可视化？

后端把一次响应拆成 `intent`、`session`、`agent_state`、`workflow`、`clarification`、`delta`、`done/error` 等事件。客户端将 Agent State 绑定到当前助手消息上方，将 Delta 增量拼接成 Markdown，并在用户主动上滑时停止自动追踪，兼顾实时反馈和历史阅读。

### Q8：鉴权和多用户隔离是如何保证的？

Access Token 有效期较短，Refresh Token 只以哈希形式存储并执行轮换和令牌族重放检测。业务接口不接受客户端传入的 `user_id`，而是从 JWT 获取当前用户；资源查询使用 `resource_id + current_user.id` 联合条件，跨用户访问统一返回 404，避免资源枚举。

### Q9：为什么 Token 日志采用旁路异步写入？

Token 统计是观测能力，不应增加对话首字延迟。LLM 调用结束后把模型、输入输出 Token、工作流和 Session 信息提交给独立线程执行数据库写入；主流程只负责生成结果。实现时需要复制上下文值，避免把 `ContextVar` Token 跨线程重置导致上下文异常。

### Q10：数据库为什么既保留 raw text，又保留结构化字段？

原始文本用于审计、重新提取和修复算法；结构化字段用于筛选、统计和趋势分析。二者同时保留可以追溯“用户说了什么”和“系统最终理解成什么”，也为未来模型升级后的离线重放提供基础。

### Q11：当前系统最大的性能瓶颈是什么？

主要是串行 LLM 调用和营养 ReAct 多轮工具循环。项目已经使用 SSE 降低感知等待，并对相互独立的数据查询使用线程池并发。后续会增加调用超时、模型降级、工具结果缓存和链路指标，区分数据库耗时、首 Token 耗时与完整生成耗时。

### Q12：如果继续开发，你会优先做什么？

第一优先级是完成 Agent 派生记忆闭环，并建立离线评估集验证意图、草稿和记忆抽取质量；第二是拆分过重的 `ChatService`，增强可测试性；第三是补齐可观测性和端到端测试，再考虑远程营养数据、训练负荷分析和产品化部署。

## 7. 面试时应主动说明的边界

- 这是可运行的个人全栈项目，不应虚构生产用户量、QPS、准确率或成本收益。
- 可以强调完成了安全闭环和跨端实现，但要明确远程 MCP 数据、生产监控和长期记忆自动提取仍在规划中。
- LangGraph 目前主要用于营养 ReAct 状态图；主 Chat Agent 使用可解释的顺序服务链，而不是为了技术标签把所有业务强行画成图。
- Android V1 已完成核心对话链路，但训练历史、周报、档案和记忆页面尚未全部移植。
